# EPD-nRF5 蓝牙协议与排障说明

本文说明 WeatherTag 如何与运行 [tsl0922/EPD-nRF5](https://github.com/tsl0922/EPD-nRF5) 固件的电子价签通信，以及 BLE 连接失败时如何判断问题所在。

文档依据上游主分支的以下实现整理：

- [`EPD/EPD_service.h`](https://github.com/tsl0922/EPD-nRF5/blob/main/EPD/EPD_service.h)：UUID、应用版本和命令编号；
- [`EPD/EPD_service.c`](https://github.com/tsl0922/EPD-nRF5/blob/main/EPD/EPD_service.c)：命令解释、通知和 RLE 解码；
- [`html/js/main.js`](https://github.com/tsl0922/EPD-nRF5/blob/main/html/js/main.js)：官方网页上位机的连接与传图流程；
- [`html/js/dithering.js`](https://github.com/tsl0922/EPD-nRF5/blob/main/html/js/dithering.js)：黑白红位面编码；
- [`html/js/rle.js`](https://github.com/tsl0922/EPD-nRF5/blob/main/html/js/rle.js)：RLE 编码及 BLE 分块方式。

## 1. 先理解传输的是什么

BLE 链路不直接传输 PNG、JPEG，也不传输天气 JSON。完整流程是：

```text
天气数据
  ↓ WeatherTag 排版
400×300 RGB 图片
  ↓ 阈值量化与逐行取模
15,000 字节黑色位面 + 15,000 字节红色位面
  ↓ 可选 RLE、按 BLE MTU 分块
EPD-nRF5 图像写入命令
  ↓ 固件写入屏幕 RAM
刷新电子墨水屏
```

因此，天气分析、文字排版和字体渲染都发生在服务器端；价签只接收已经取模的像素数据并驱动屏幕。

## 2. GATT 服务与特征

| 用途 | UUID | 属性 | 数据 |
| --- | --- | --- | --- |
| EPD 服务 | `62750001-d828-918d-fb46-b6c11c675aec` | Primary service | 包含以下两个特征 |
| 命令/数据 | `62750002-d828-918d-fb46-b6c11c675aec` | Write、Write Without Response、Notify | 客户端向价签发送命令；价签向客户端通知配置、MTU 和时间 |
| 应用版本 | `62750003-d828-918d-fb46-b6c11c675aec` | Read | 单字节固件应用版本，例如当前上游 `0x1a` |

WeatherTag 要求应用版本不低于 `0x16`，因为它使用从 v1.6 引入的 `WRITE_IMAGE (0x30)`。应用版本不是屏幕驱动型号；屏幕驱动和引脚仍使用价签固件中已经保存的配置。

上游服务把这两个特征配置为开放访问，不要求应用层账号、令牌或配对加密。它适合家庭内短距离设备控制，但不应把能修改引脚、配置或系统状态的命令暴露给不可信客户端。WeatherTag 不使用这些危险命令。

## 3. WeatherTag 的连接和传图顺序

一次屏幕更新按以下顺序执行：

1. 根据 `ble.address` 扫描设备；未配置地址时按 `ble.name` 精确匹配广播名称。
2. 建立 BLE 连接并发现 GATT 服务。
3. 读取应用版本特征，低于 `0x16` 时终止。
4. 订阅命令/数据特征的通知。
5. 发送 `INIT`，让固件按已保存的驱动型号初始化，并等待能力通知。
6. 先发送黑色位面，再发送红色位面。
7. 发送 `REFRESH`，让屏幕显示 RAM 中的新图像。
8. 断开连接；屏幕无需持续供电即可保持内容。

订阅通知后，固件通常先发一包二进制设备配置。收到 `INIT` 后还会发出：

```text
mtu=244 rle=1
t=1787875200
bat=2987
```

`mtu` 是特征单次可承载的最大总字节数，不是纯图像数据长度。`rle=1` 表示支持快捷传图的 RLE，`t` 是价签中的时间，`bat` 是毫伏单位的电池电压。WeatherTag 不修改收到的设备配置；它会保存本次连接读取的 `bat`，并在下一次屏幕刷新中显示，因此不会为了电池信息增加额外 BLE 连接。

如果两秒内没有收到 MTU 通知，WeatherTag 会采用 BlueZ 报告的保守 MTU，并关闭 RLE；这和建立 BLE 连接超时是两个不同阶段。

## 4. WeatherTag 使用的命令帧

所有帧都写入命令/数据特征，第一字节是命令编号。

| 操作 | 帧格式 | 说明 |
| --- | --- | --- |
| 初始化 | `01` | 使用设备已保存的驱动型号；固件随后通知 MTU、RLE 和时间 |
| 写图像 | `30 flags data...` | 把一块图像数据写入屏幕 RAM |
| 刷新 | `05` | 用已写入的 RAM 数据刷新电子墨水屏 |

GATT 对 `05` 的写入确认只说明固件已经接收命令，不等于电子墨水屏已经完成物理刷新。部分扩展固件会异步执行较长的三色刷新；如果客户端收到写入确认后立即断开，固件可能在断连处理里让屏幕休眠，截断刷新波形。表现通常是屏幕闪烁时间明显变短、内容完整但颜色很淡。

WeatherTag 因此会在发送 `05` 后继续保持 BLE 连接，默认等待 25 秒再退出连接。可用 `ble.refresh_wait_seconds` 调整；寒冷环境或刷新时间较长的面板可适当增加。

`WRITE_IMAGE` 的 `flags` 是位标志：

| 位 | 值 | 含义 |
| --- | --- | --- |
| bit 0 | `0` / `1` | `0` 写黑色位面，`1` 写红色位面 |
| bit 1 | `1` | 当前块是该位面的第一块，固件应重置写入位置 |
| bit 2 | `1` | 当前块使用 RLE 编码 |

例如：

- 黑色位面第一块、未压缩：`30 02 ...`；
- 黑色位面后续块、未压缩：`30 00 ...`；
- 红色位面第一块、RLE：`30 07 ...`；
- 红色位面后续块、RLE：`30 05 ...`。

上游固件还支持清屏、睡眠、时间同步、原始屏幕命令、修改引脚/配置、系统重置等命令。WeatherTag 刻意只使用 `INIT`、`WRITE_IMAGE` 和 `REFRESH`，避免自动服务意外改写价签的硬件配置。

固件中定义的完整命令概览如下。除前三个 WeatherTag 子集外，其余是理解上游上位机或调试固件时的参考，不建议手工尝试：

| 编号 | 上游名称 | 作用 | WeatherTag |
| --- | --- | --- | --- |
| `00` | `SET_PINS` | 改写 EPD GPIO 引脚映射并保存 | 不使用 |
| `01` | `INIT` | 初始化当前或指定的屏幕驱动 | 使用，不指定新驱动 |
| `02` | `CLEAR` | 清除屏幕 | 不使用 |
| `03` | `SEND_COMMAND` | 直接向屏幕控制器发送底层命令 | 不使用 |
| `04` | `SEND_DATA` | 直接向屏幕控制器发送底层数据 | 不使用 |
| `05` | `REFRESH` | 刷新屏幕 | 使用 |
| `06` | `SLEEP` | 让屏幕驱动进入睡眠 | 不显式使用；断开时固件会处理 |
| `20` | `SET_TIME` | 同步 Unix 时间、时区和显示模式 | 不使用 |
| `21` | `SET_WEEK_START` | 设置一周起始日 | 不使用 |
| `30` | `WRITE_IMAGE` | 向屏幕 RAM 顺序写入图像位面 | 使用 |
| `90` | `SET_CONFIG` | 覆盖固件配置结构并保存 | 不使用 |
| `91` | `SYS_RESET` | 重启 MCU | 不使用 |
| `92` | `SYS_SLEEP` | 让 MCU 进入系统睡眠 | 不使用 |
| `99` | `CFG_ERASE` | 擦除配置并重启 | 不使用 |

## 5. 400×300 黑白红图像格式

每个位面按从上到下、每行从左到右排列。每个字节容纳连续 8 个像素，最左像素位于最高位 bit 7：

```text
byte_index = y × 50 + floor(x / 8)
bit_index  = 7 - (x mod 8)
```

单个位面大小为 `400 × 300 ÷ 8 = 15,000` 字节，两个位面共 30,000 字节。WeatherTag 与官方上位机使用相同的极性和阈值：

| 像素 | 黑色位面 | 红色位面 | 屏幕结果 |
| --- | --- | --- | --- |
| 白 | `1` | `1` | 白 |
| 黑 | `0` | `1` | 黑 |
| 红 | `0` | `0` | 红色位面优先，显示红色 |

当前实现面向需求指定的 4.2 寸 400×300 三色屏，适配 EPD-nRF5 中的 4.2 寸 UC8176/SSD1619 常规双位面传输。上游网页对部分 UC8159 大屏型号还会把两平面转换为每像素 4 bit 的数据；WeatherTag 当前不支持这类非目标屏幕。

## 6. MTU、分块与写入确认

每个图像包还要占用两个字节：`0x30` 命令和 `flags`。因此纯图像块的最大长度为：

```text
chunk_size = device_reported_mtu - 2
```

例如设备通知 `mtu=244` 时，每块最多发送 242 字节图像数据。默认每 20 个包使用一次 Write With Response，其余使用 Write Without Response，最后一包始终要求响应。`ble.write_ack_interval` 可以调整这个间隔；较小的值更稳但更慢。

## 7. RLE 格式

RLE 只在设备通知 `rle=1` 且压缩后确实更小时使用。控制字节定义如下：

| 控制字节 | 后续数据 | 解码结果 |
| --- | --- | --- |
| bit 7 为 `1` | 1 字节重复值 | 重复次数为 `(control & 0x7f) + 3`，即 3～130 次 |
| bit 7 为 `0` | `control + 1` 字节原文 | 复制 1～128 个字节 |

固件逐个 BLE 包解压，所以一个 RLE 代码不能横跨两个包。WeatherTag 会先按完整 RLE 代码边界分块，再决定是否采用压缩结果。

## 8. 当前连接超时的含义

这次堆栈停在 Bleak/BlueZ 的 `BleakClient.connect()`，随后由 `asyncio.timeout` 抛出 `TimeoutError`。结合 WeatherTag 的调用顺序，可以确定：

- 本轮扫描已经找到了配置的设备，否则会得到“未发现电子价签”；
- 失败发生在 BLE 链路建立阶段；
- 尚未读取固件版本、订阅通知、协商 MTU 或发送图片；
- 因而暂时不能归因于 EPD 命令、RLE 或图片位面。

扫描到广播不代表一定能连接。扫描主要接收入站广播，而连接要求电脑与价签之间维持稳定的双向 2.4 GHz 通信。电脑没有安装蓝牙/Wi-Fi 天线时，近距离偶尔看到广播、连接却持续超时是合理现象。应先安装主板要求的天线，并把价签放到电脑附近测试，不建议先靠增大超时时间掩盖射频问题。

## 9. 建议排查顺序

### 9.1 射频和设备状态

1. 正确安装主板或蓝牙网卡配套天线，首次测试距离控制在 0.5～1 米。
2. 确认价签供电正常、已经唤醒并正在广播。
3. 关闭可能连接着价签的官方网页、手机或其他 BLE 客户端。
4. 连续执行几次 `scan-ble`，确认同一设备能稳定出现，而不是偶尔出现一次。

### 9.2 用 BlueZ 隔离应用问题

先检查适配器没有被禁用：

```bash
rfkill list bluetooth
bluetoothctl show
```

然后进入 `bluetoothctl`，观察扫描并尝试建立最基础的连接：

```text
power on
scan on
connect AA:BB:CC:DD:EE:FF
info AA:BB:CC:DD:EE:FF
disconnect AA:BB:CC:DD:EE:FF
quit
```

如果 `bluetoothctl connect` 也超时，问题位于天线、距离、适配器、BlueZ 或价签状态，不在 WeatherTag 协议层。如果它能稳定连接，再运行 `weathertag run-once` 检查固件版本和 GATT 协议。

也可以用手机打开 [EPD-nRF5 官方网页上位机](https://tsl0922.github.io/EPD-nRF5/) 测试。手机可连接而服务器电脑不可连接，通常说明服务器的蓝牙射频或 BlueZ 环境有问题。

### 9.3 检查 WeatherTag 配置

地址优先于名称。使用固定地址时建议只保留地址，避免误解实际匹配方式：

```toml
[ble]
enabled = true
address = "AA:BB:CC:DD:EE:FF"
name = ""
connect_timeout_seconds = 20
retry_attempts = 3
write_ack_interval = 20
refresh_wait_seconds = 25
```

如果多次扫描得到的地址会变化，则清空 `address`，改用唯一的广播名称。名称匹配是精确匹配，同名设备可能造成误选。

确认射频链路稳定后，如果设备只是偶尔建立连接较慢，可把 `connect_timeout_seconds` 调到 30；连续超时时继续增加通常没有帮助。

## 10. 按错误阶段定位

| 日志或异常 | 已到达的阶段 | 优先检查 |
| --- | --- | --- |
| `未发现电子价签` | 扫描未匹配 | 地址/名称、唤醒、广播、距离、天线 |
| `BLE 操作超时`，底层在 `connect()` | 找到广播但未建链 | 天线、信号、其他客户端占用、BlueZ |
| `无法读取 EPD-nRF5 固件版本` | 已连接并发现服务 | 是否刷入正确固件、GATT 服务是否匹配 |
| `固件版本 ... 过旧` | 已读取版本 | 升级到 `0x16` 或更新固件 |
| `设备未报告 MTU` | 已连接并发送 `INIT` | 通知能力；程序会自动保守降级，不一定失败 |
| 写图像时断开或超时 | 已开始传输 | 信号稳定性、确认间隔、供电、固件/驱动配置 |
| 闪烁明显短于官方工具、画面很淡 | 已接收刷新命令但物理刷新被截断 | 增加 `refresh_wait_seconds`，确保完成后再断开 |
| 已传完但画面错误 | 已刷新屏幕 | 屏幕驱动型号、引脚、分辨率和位面格式 |
