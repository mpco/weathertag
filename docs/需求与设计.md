# WeatherTag 需求分析与方案设计

## 一、项目概述

### （一）项目背景

随着家庭服务器、物联网设备和电子墨水屏技术的发展，低功耗信息展示设备逐渐具备家庭应用价值。传统天气应用虽然能够提供大量天气数据，但用户在出门前通常只需要快速了解几个关键信息：当前天气如何、温度多少、是否降雨、是否存在天气预警以及是否需要携带雨具或调整衣物。

WeatherTag 项目计划利用二手三色电子价签设备，将其改造为家庭入户天气信息屏，安装在入户门内侧，为家庭成员提供“出门前快速查看天气”的场景化信息服务。

### （二）项目定位

WeatherTag 不定位为完整天气信息终端，也不追求展示大量天气指标，而定位为：

> 一个面向家庭日常出行场景的低功耗天气提醒屏，将天气服务提供的数据转换为直观、易理解的信息，在用户出门前提供快速参考。

核心目标：

* 查看当前天气状态；
* 快速了解当前温度及体感；
* 判断近期是否需要携带雨具；
* 关注天气预警和异常天气；
* 了解未来几天天气趋势。

### （三）设计原则

WeatherTag 遵循以下原则：

**简单可靠原则。** 系统长期运行在家庭环境中，应避免复杂设计，优先保证稳定运行。

**信息转换原则。** 对于用户能够直接理解的信息直接展示，对于需要专业知识转换的数据进行简单映射，但不进行复杂预测或智能评分。

**低维护原则。** 尽量减少人工干预，具备自动恢复、错误通知和运行状态记录能力。

**低功耗原则。** 充分利用电子墨水屏断电保持显示的特点，降低刷新频率。

# 二、系统总体方案

## （一）硬件方案

目标设备：

* 盒马 4.2 寸三色电子价签；
* 分辨率约 400×300；
* 黑、白、红三色电子墨水屏；
* 基于 nRF52811 等 BLE 控制方案；
* 使用开源项目 EPD-nRF5 固件。

电子价签主要负责：

* 接收 BLE 图像数据；
* 刷新电子墨水屏；
* 保持显示内容。

复杂逻辑均由服务器完成。

---

## （二）软件总体架构

系统结构：

```
和风天气 API
       |
       |
 WeatherTag 服务
       |
       ├── 天气数据获取
       |
       ├── 天气状态分析
       |
       ├── 出门提示生成
       |
       ├── 图片渲染
       |
       └── BLE发送
              |
              |
        电子墨水屏
```

运行环境：

* Linux 家庭服务器；
* Python 实现；
* systemd 服务运行。

蓝牙通讯协议参考： 相关开源代码 https://github.com/tsl0922/EPD-nRF5

# 三、功能需求

## （一）天气数据获取

天气数据来源：

* 和风天气 API。

认证方式：

* JSON Web Token（JWT）。

获取内容包括：

* 当前天气；
* 分钟级降水趋势；
* 小时天气预报；
* 未来三天天气；
* 天气预警信息。

第一阶段只使用单一固定地点配置，不考虑多地点管理。

---

## （二）天气信息展示

WeatherTag 不直接复制天气 API 返回数据，而进行适合家庭查看的整理。

顶部状态栏显示日期与星期、更新时间，以及电子价签上次 BLE 连接读取的电池电压。电池以图标和电压值表示，不推算百分比；首次运行尚无读数时显示未知值。

### 1. 当前天气

主要显示：

* 天气状态；
* 当前温度；
* 体感温度。

示例：

```
☁  28℃
多云 · 体感30℃
```

---

### 2. 今日天气

今日最高温、最低温、风力和湿度合并到三日预报的“今”区域，避免与独立今日卡片重复。

示例：

```
今 ☀ 24~32℃
东南风3级 · 湿度60%
```

---

### 3. 短时降雨

重点服务“是否需要带伞”的场景。

显示方式：

* 无明显降雨：

```
未来2小时无明显降雨
```

* 即将降雨：

```
约30分钟后可能有雨
```

* 当前降雨：

```
正在降雨
```

可结合简单趋势图展示未来2小时降水变化。

---

### 4. 未来三天天气

用于趋势参考。

显示：

```
今 ☀ 25~31℃
明 ☁ 24~30℃
后 ☂ 23~28℃
```

固定使用“今、明、后”标识，避免星期文字增加识别负担，也不显示额外标题或过多详细指标。

正常界面使用少量语义红色强调当前温度单位和“今”标签；降雨、天气预警和重要提醒继续使用红色。颜色用于区分信息含义，不把分隔线等纯装饰元素大面积设为红色。

---

# 四、天气分析与提醒设计

## （一）设计原则

天气分析模块不采用复杂评分模型，不引入人工智能判断。

采用：

> 数据获取 → 简单规则转换 → 生成直白提示。

目标是让用户看到一句容易理解的话，而不是展示复杂计算结果。

---

## （二）提醒规则

按照固定优先级处理：

### 1. 天气预警

最高优先级。

例如：

```
🔴 暴雨预警，注意出行安全
```

---

### 2. 当前降雨

例如：

```
正在下雨，建议带伞
```

---

### 3. 即将降雨

根据分钟级降水：

例如：

```
30分钟后可能有雨，建议带伞
```

---

### 4. 极端温度

例如：

```
今日高温，注意防晒
```

或：

```
天气寒冷，注意添衣
```

---

### 5. 温差提醒

例如：

```
昼夜温差较大，注意增减衣物
```

---

### 6. 普通天气

无特殊情况：

```
天气良好，适宜出行
```

---

## （三）提醒显示原则

屏幕只显示一条最高优先级提醒。

避免同时显示：

* 降雨提醒；
* 高温提醒；
* 空气质量提醒；

造成信息干扰。

---

# 五、电子墨水屏界面设计

## （一）总体布局

400×300 横屏固定布局：

```
┌──────────────────────────┐
│ 日期 星期        更新时间 │
│                          │
│          天气图标          │
│                          │
│           28℃             │
│          多云             │
│          体感30℃          │
│                          │
│ 今日24℃～32℃              │
│ 风力 东南风3级 湿度60%    │
│                          │
│ 未来2小时降水趋势          │
│ ▂▂▅▇▅▂                  │
│                          │
│ 🔴 下午可能有雨，建议带伞 │
│                          │
│ 六☀25~31 日☁24~30         │
└──────────────────────────┘
```

---

## （二）颜色使用

三色屏：

黑色：

* 普通文字；
* 数字；
* 图标。

红色：

仅用于：

* 天气预警；
* 降雨提醒；
* 高温、寒潮等异常情况。

不将红色作为装饰颜色。

---

## （三）更新时间

屏幕显示：

```
更新 17:30
```

用于判断信息新鲜度。

# 六、更新策略

## （一）定时更新

建议：

```
06:00-09:00
30分钟

09:00-18:00
60分钟

18:00-23:00
30分钟

23:00-06:00
低频更新
```

---

## （二）天气变化触发更新

以下情况立即更新：

* 天气预警变化；
* 无雨变有雨；
* 有雨变无雨；
* 明显天气状态变化；
* 温度明显变化。

普通小变化等待下一次定时更新。

---

# 七、异常处理设计

## （一）天气 API 异常

处理流程：

```
获取失败
   ↓
自动重试
   ↓
仍失败
   ↓
进入异常状态
```

默认：

* 重试若干次；
* 失败后记录错误；
* 发送 Gotify 通知。

---

## （二）天气数据失败显示

如果无法获取最新天气：

屏幕显示：

```
⚠ 天气数据获取失败

暂时无法更新天气信息

最后更新：
08月21日 08:30
```

保留最后一次成功时间。

---

## （三）电子价签连接异常

如果：

* BLE无法连接；
* 图片发送失败；
* 刷新失败；

处理：

* 自动重试；
* 记录日志；
* Gotify通知。

示例：

```
WeatherTag

电子价签更新失败

原因：
BLE连接失败
```

---

# 八、通知与日志设计

## （一）通知方式

使用 Gotify。

通知：

* 天气 API 连续失败；
* BLE 更新失败；
* 设备异常。

不通知：

* 正常刷新；
* 普通天气变化。

---

## （二）运行记录

保存：

* 最后天气更新时间；
* 最后屏幕更新时间；
* 错误日志。

第一阶段不引入数据库。

---

# 九、开发方案

## （一）技术栈

开发语言：

Python。

主要组件：

* requests/httpx：天气 API；
* Pillow：图片渲染；
* bleak：BLE通信；
* systemd：服务管理。

---

## （二）模块划分

建议结构：

```
WeatherTag

├── weather.py
│   天气API访问

├── rules.py
│   天气转换规则

├── renderer.py
│   图片生成

├── epd.py
│   BLE通信

├── notifier.py
│   Gotify通知

├── config.py
│   配置管理

└── main.py
    主程序
```

# 十、开发阶段规划

## 第一阶段：界面开发

无需电子价签。

完成：

完成：

## 项目最终目标

WeatherTag 建成后，实现：

> 一个安装在家门口、低功耗、无需操作、自动更新的家庭天气信息牌，在每天出门前用几秒钟告诉家人“现在天气如何、是否需要带伞、是否需要注意特殊天气”。
